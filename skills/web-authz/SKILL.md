# 越权 / 访问控制(Broken Authorization)

应用未正确校验"当前主体是否有权访问该对象/功能",导致越权读写。

## 类型

- **水平越权 / IDOR**:换一个对象 id 就能访问他人数据(可预测/可枚举的对象引用)。
- **垂直越权**:低权限用户触达高权限功能(缺少角色校验的接口/路由/按钮背后的 API)。
- **功能级缺失**:前端隐藏但后端未校验的接口。

## 白盒信号

- 控制器/路由上**缺少**鉴权中间件或 `authorize/can/policy` 检查;
- 只校验"登录态"却不校验"对该对象的所有权/角色";
- 直接用请求里的 id 查询而不加 `where owner = current_user`;
- 前端做权限、后端信任前端。

## 黑盒检测与验证(按 ROE)

- 准备**两个不同权限/不同归属的账号**(或一个账号 + 未授权请求)。用 A 的会话去访问 B 的对象 / 高权限接口。
- **只读证明优先**:能**读到**本不该读的他人数据 / 高权限数据即可证明越权——这在 `safe_validate`(严格不改数据)下完全可做。
- 改动型越权(越权**写/删**他人数据):`safe_validate` 下**不要真改**,改为用只读接口证明能定位/读取,并依据代码推断可写、标注"未实际改动";更高约束+审批下才做改动验证。
- 用最小对比证据:同一请求换 id/换账号的响应差异 + 截图。

## 严重度要点

能读到/操作到的**具体数据或功能**是什么、规模多大、需要什么前提(匿名可达 ≫ 需要某账号)。只换 id 返回 404/403 不算;要实际拿到不该拿的内容。

边界与报告规范见 `web-app-pentest/references/methodology.md`。
