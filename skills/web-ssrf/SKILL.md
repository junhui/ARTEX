# 服务端请求伪造(SSRF)

应用把**用户可控的 URL/地址**交给服务端去请求,攻击者借此让服务器访问其本不该访问的目标(内网、云元数据、本机服务)。

## 哪里找

- URL 抓取 / 预览 / 缩略图 / 导入(from URL)/ Webhook / 回调 / 文件/图片远程拉取 / PDF 渲染 / SSO 元数据地址 / 代理转发。

## 白盒信号

- **source**:参数里的 URL/host/port/路径。
- **sink**:`http client.get(输入)`、`requests/axios/fetch/curl(输入)`、`URL.openConnection`、图片/文件库按 URL 加载。
- 缺少**出站白名单 / 协议限制 / 内网地址拦截 / 重定向跟随控制**;对 DNS 重绑定无防护。

## 黑盒检测与验证(按 ROE)

- 把可控 URL 指向**可控且可证明的带内目标**:优先让服务端请求回到**目标自身**的某个可区分端点(证明"由服务端发起"),或请求一个会在**响应里体现差异**的地址。
- 内网/元数据验证要**克制**:可尝试云元数据(如 `169.254.169.254`)等高价值内网目标以**读取**证明可达,但**不要抓取、外传或滥用拿到的凭据/敏感数据**;点到为止、只证可达。
- **只走带内**:SSRF 常依赖带外(DNS/HTTP 外连)。只能靠带外证明的,记 `blocked` + 代码级证据,不搭外部回连设施。
- 不做端口大扫、不对内网做破坏性操作。

## 严重度要点

能否读到云元数据/凭据、能否打到内部高价值服务,是定级关键;只证"服务端会请求任意外部 URL"但够不到任何敏感目标,影响有限。按四问 + 只计你实际演示到的范围。
